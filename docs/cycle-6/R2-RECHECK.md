## 2. 为什么不能沿用旧通过数

本轮先重跑 37 项带 A01–A12 / G01 名称的旧回归，全部通过；随后新增的首批 7 项公开接口检查全部失败。主要原因是旧测试只检查返回的 `next_block`，没有把它交回公开读取接口；只检查 renderer 的 partial，没有覆盖 PDF 最后一页内截断和 Word 表格裁列 / 多字节单元格。

再补搜索穷尽和告警裁剪检查后，又复现了目录只读第一页、扫描预算包含已跳过前缀导致游标空转、告警数组有界裁剪却没有总数与截断说明。上述问题已修复。A09 的写入异步时序、A11 无任务启动仍可通过的断言也已加强。

失败的测试夹具另行记录：第一版 PDF 长行延伸到合成页的 MediaBox 外，真实解析结果不能拿输入字符串当作全部可见文本；已改为页内可见文本、多页和页内切分验证。它不是产品丢字的证据。中间一次全套检查为 372 / 373，唯一失败是加强后的 A11 暴露非法空附件；修正夹具后再跑完整套件。

## 3. G01 / C6-I036 的当前证据

[parse-responsiveness.test.mjs](../../agent-runtime/test/parse-responsiveness.test.mjs) 现在在真实 PDF 开始请求第一页后安排取消，并输出心跳与取消测量。最终完整套件中的一次观测如下：

| 观测 | 本次值 |
| --- | --- |
| 合成 PDF | 300 页，93,508 bytes |
| 整次读取耗时 | 749.2 ms |
| 读取期间心跳次数 / 最大心跳间隔 | 18 次 / 473.3 ms |
| 取消场景首次请求页的时刻 | 开始后 10.6 ms |
| 取消回调运行 / 读取以 `aborted` 拒绝 | 开始后 25.1 / 28.0 ms |
| 取消前实际请求页数 | 15 页，未完成 300 页读取 |

这些是该夹具、当前机器、完整套件并行负载下的观测，**不是所有文档的固定延迟保证**。每 16 页让步证明页循环能接收取消；不能抢占的加载或单次同步解析区段仍存在，不能据此承诺立即取消、固定 174 ms 或整个解析的硬时间上限。

旧测试把同一份 300 页 PDF 拼接两次并断言耗时小于 200 ms，没有构造超出 2,000 页的文档，也没有证明“解析前拒绝”。已替换为确定性 loader：返回 2,001 页元数据后，确认尚未调用 `getPage` 就以 `document_too_complex` 拒绝并销毁文档。该测试证明提取前的页数校验，不证明加载前或加载阶段的耗时上限。页范围测试也改为核对实际返回范围，去掉机器负载相关的速度比较断言。
