# Aside v1 范围界定

日期：2026-11-05。状态：**范围提案，待用户确认后生效。** 本文定义第一版发布承诺什么、不承诺什么，以及判定"可以做 v1 了"的条件。它不替代 [RECOVERY-PLAN.md](./RECOVERY-PLAN.md) 的遗留项跟踪，也不把任何未执行的人工验收改成已通过。

## 1. 为什么需要这份文档

Cycle 5–8 的开发范围每次都由上一条需求推出来，没有一条"到此为止"的线。结果是：功能都在变多，而**发布能力从 Cycle 6 起一直标为"无限期延期"**，从未排期。核查当前源码后确认：

- `src-tauri/resources` 从未 staging（`scripts/stage-runtime.mjs` 存在，但没有执行过）；
- 没有产出过安装包；
- 干净环境安装验证从未执行。

也就是说，离"能发布"最远的不是功能缺口，而是**发布本身**。v1 范围因此按"安装后产品承诺什么"来界定，而不是按"代码里实现了什么"。功能可以留在代码里但不作为 v1 承诺——这是控制范围的唯一可持续做法，因为它不需要删代码。

## 2. v1 的一句话定义

> 一个 Windows 用户，从安装包开始，**不编辑任何配置文件**，能用真实厂商模型完成文件与文档任务，操作有审批，结果落在默认目录，会话可保存找回，并且能卸载干净。

这句话拆成六条承诺，每条都必须有实机证据（见 [V1-ACCEPTANCE.md](./V1-ACCEPTANCE.md)）：

| # | 承诺 | 对应的现有能力 | 缺什么 |
| --- | --- | --- | --- |
| V1.1 | 装得上、起得来、卸得净 | `stage-runtime.mjs`、`runtime.rs` 的资源解析 | 从未构建过安装包；无干净机器验证 |
| V1.2 | 零配置连上真实模型 | P0/P1 设置、凭据、四家 catalog | 四家真实厂商连通性从未验证 |
| V1.3 | 能用真实文件与文档完成任务 | RT-04–07 文件、PDF、Word、写入审批 | 真实 Word 打开、真实 Explorer 定位未验证 |
| V1.4 | 会话可新建、切换、重启找回 | P4 会话管理 | 真实桌面面板交互未验证 |
| V1.5 | 出问题时说清楚，且不泄露 | 诊断、错误脱敏、逐次审批 | 真实故障场景（离线、错 key、只读目录）未演练 |
| V1.6 | 不用自己维护工作区，继续上次的工作 | 尚无；`continuation` 只在单会话内有效 | 工作索引整体未实现，见第 3 节 |

## 3. v1 的核心差异化：工作索引

这是 Aside 与"Pi 套壳"的分界线，必须写进 v1，否则这一版只是把一个 agent 装进侧栏。

### 3.1 Memory 在这里的含义

项目文档把记忆分三层："当前任务的工作状态、历史任务的摘要与决定、长期稳定的偏好和事实"
（[PRODUCT-DIRECTION.md](./PRODUCT-DIRECTION.md#memory-与自整理)）。本产品的 memory 是
**第二层的工作索引**，不是第三层的内容式个人数据：

| | 要 | 不要 |
| --- | --- | --- |
| 存什么 | 任务、任务涉及的文件与产物、任务间关系 | 用户偏好、个人画像、软件使用习惯 |
| 怎么形成 | 确定性代码在任务结束后登记 | 自动摘要对话、向量检索 |
| 谁消费 | 下一次任务开始时作为上下文供给 | 个性化推荐 |
| 能否删除 | 必须能查看、纠正、删除 | 全自动不可见 |

原文的警告仍然适用：全量保存聊天、引入向量库，本身不能证明"下次少解释、准确接续"这个目标。

### 3.2 工作索引要解决的问题

用户的现状：同时在做两件事（例如开发软件、写简历）。传统上要建两个工作区，每次继续做要先自己
找到上次的会话，再决定是新开还是接着做。

目标：**用户不再维护工作区**。Aside 在后台维护工作记录，用户只需开始说要做的事，系统判断
这属于哪个已有工作，还是一个新工作。用户不满意时可以要求它分离或归并。

```text
用户发起任务 → 判断归属（新工作 / 已有工作）
            → 载入该工作的文件与产物范围
            → 执行并接回产物
            → 登记到该工作（文件、产物、时间、一句话结果）
```

### 3.3 形态（待实现时细化）

- **记录是普通文件**，不是向量库。这样用户能直接看、能手动改、能随目录打包带走。
- **判断归属**由模型读索引后决定，不写死在代码里做相似度匹配。索引提供的是可读材料，
  归并是模型给出、用户可推翻的判断。
- **分离 / 归并是显式操作**：用户让 agent 做，agent 改索引文件，与改普通文档没有区别。
- 具体字段、文件布局、与现有 `continuation`（会话内 workspace 延续）的关系都没定。
  当前 `continuation` 只在单个会话内有效，工作索引需要跨会话成立，这是实现时第一个要解决的问题。

### 3.4 v1 做到哪一步

v1 只需要证明**这条链能走通一次**，不追求判断准确率高：

- 两次不相关的任务被登记为两条记录；
- 第三次与第一条相关的任务能被归入第一条；
- 用户能看到记录内容，能让 agent 拆分或合并；
- 归错时用户能纠正，纠正后不反复。

这一条不满足，v1 就只是一个普通 agent 外壳，`V1.6` 承诺随之失效（见下）。准确率、自动建议、
跨设备同步都不在 v1。

## 4. v1 明确不做

以下**不是 backlog**，是本版不承诺。它们在代码里可能存在，但不作为 v1 的一部分被验收、被宣传、被支持。

| 不做 | 为什么 |
| --- | --- |
| 长期偏好、事实库、自动摘要、跨引擎会话迁移 | 见第 3 节：这些是"内容式记忆"，不是本产品的 memory。工作索引（索引式）不在本行 |
| 自动 / 持续 context capture、后台主动建议 | 用户明确：capture 始终手动触发，只有快捷键这一种入口。自动判断"用户此刻在处理什么"超出边界，属于越界而非优先级问题 |
| Codex / Claude Code 等外部 agent 接入 | 需要各自协议、权限与验证范围；独立 feature |
| Mac | 无排期；平台专属外壳的投入需要单独权衡 |
| 第一方 Web 搜索 | Cycle 6 已明确撤销，不自动转交 |
| 任意 shell / 命令执行 | 权限模型无法给"任意命令"一个可解释的边界 |
| 远程 MCP（HTTP / OAuth）、服务市场 | 需要独立的传输、凭据与信任模型 |
| 多 provider profile、项目级配置 | 单用户单配置已满足 v1 承诺 |
| 会话搜索 / 导出 / 分支 / 并行任务 | P4 边界已写明；不影响"能找回会话" |
| 会话压缩与长对话续接 | 超出上下文时的失败要可理解（见 V1.5），但"压缩后继续"不是 v1 |
| 手动 skill 选择器 | 内建 skill 自动激活已够用；选择界面是后续 |
| 安装包签名、自动更新、多语言 | 与"能安装并运行"无关，属于分发工程 |

## 5. 冻结规则

v1 范围一经确认，按以下规则执行，防止重新膨胀：

1. **新需求先问归属。** 是 v1 修 bug/补证据，还是 v1 之后的 feature？后者进入 [PRODUCT-DIRECTION.md](./PRODUCT-DIRECTION.md)，不进本周期。
2. **只修 V1 承诺内的缺陷。** 承诺外的既有缺陷记录在案、不阻塞 v1，也不趁手顺带修。
3. **不加新面板、新配置项、新协议消息**，除非某项验收（V1-ACCEPTANCE.md）明确需要。修验收暴露的问题不算加功能。
4. **每项 v1 工作必须能指向某条承诺。** 指不上的，不做。
5. **范围变更只有用户能批准**，并在此文档记录变更日期与原因。

## 6. 判定"v1 可以发布"的条件

全部满足才算，缺一不可：

- [V1-ACCEPTANCE.md](./V1-ACCEPTANCE.md) 中 A 组（安装与启动）全部通过；
- B 组（真实模型）至少一家厂商全流程通过，四家 catalog 均可选；
- C 组（文件与文档）与 D 组（会话）全部通过；
- E 组（错误与安全）全部通过；
- F 组（工作索引）全部通过——它是 v1 区别于普通 agent 外壳的唯一证据；
- 根质量门禁通过（typecheck / build / runtime / frontend / Rust）；
- 已知缺陷清单已复核：v1 承诺内的阻断项为零。

不满足条件时的正确动作是**修到满足或下调承诺**，不是把未执行的项标成通过。这一点沿用 Cycle 6 审计的结论（[C6-I035](./cycle-6/ISSUES.md)）。
