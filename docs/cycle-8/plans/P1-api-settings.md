# P1：API 与模型设置

日期：2026-11-01。状态：开发与自动验证完成；真实厂商连通性、原生整体验收和安装包仍未验证。批次：C8.1。问题见 [ISSUES.md](../ISSUES.md)。

## 范围与用户结果

用户从界面配置现有四种 provider、Base URL、受支持模型与 API key，保存后看到应用状态，并能显式测试连接。设置入口在模型不可用时仍可进入。

## 计划

1. 用 P0 的设置服务构建一个复用当前组件的设置入口；展示有效值、来源与覆盖原因。
2. 在原生层实现 Windows 凭据管理器读写，凭据只通过专门写入命令提交，读回为脱敏状态；保留环境优先级和旧 env 兼容。
3. 由 runtime 返回所选 provider 的受支持模型与能力；不让 React 依赖 Pi，也不把任意模型 ID 当作兼容。
4. 提供显式最小模型请求测试；说明将访问所配端点并产生少量用量，失败不误标连接成功。
5. 空闲时安全重建 runtime 应用配置，保存中的任务继续使用原快照；清理旧 MCP、权限与迟到事件，保留会话。

## 验收边界

错误 key、无效 URL、不可达端点、存储失败及环境覆盖有明确状态。密钥不进入普通设置、日志、聊天或通用事件。任务中修改只显示待应用，不重置任务。支持 provider 的真实连通性与 fixture 结果分别记录。

验证包含配置控制、凭据失败、模型能力、重建竞态和设置表单测试，类型 / 构建与相关 Rust 测试。不增加 OAuth 登录、profile、项目层、自动发现或新 provider。

## 实施约定

- 密钥存入当前 Windows 用户的 Credential Manager generic credential，按 provider 分开；独立写入 / 删除命令，读取仅返回配置状态。原生到 Node 的私有 stdin 信封传递凭据，普通设置文件、命令行参数和前端读回不含密钥。优先级为进程环境 > 系统凭据 > 旧 env。
- 设置控制助手按需加载 provider catalog，连接测试直接调用同一 provider 选择逻辑，不初始化会话、skills 或 MCP；测试已保存的有效配置，默认不联网。
- 保存与应用分开。显式应用在协议层排队，等待 prompt、会话落盘和 workspace 操作全部结束，再在同一进程重建 agent；沿用活动 session 与内存消息。候选初始化失败保留旧实例。
- 成功切换先关闭旧 MCP / 权限 broker，再发布新 ready；旧实例 emitter 失效。前端保留聊天、草稿和捕获附件，重置旧权限 / 工具状态。原生快照报告实际加载版本、待应用 / 应用中 / 失败状态。
- 界面只增加“模型与 API”设置面板及入口，沿用当前宽度与圆角；默认目录、思考控制、会话管理、MCP 编辑留在各自计划。

## 执行记录

- 已实现头部设置入口与 `SettingsPanel`，provider 未配置 / 初始化失败也能进入。显示普通设置有效值、来源及环境覆盖；普通保存、key 保存 / 删除、应用、连接测试各自独立。普通保存不会丢掉尚未提交的 key；主动重载、切换 provider 或成功保存 key 才清空输入。
- 原生凭据使用 `Aside/API/<provider>` 的当前用户 generic credential。凭据不写入 `settings.json`，不通过普通事件 / 参数读回；损坏的单个存储条目不阻断设置页，仍提供替换 / 删除。环境 key 优先于系统存储，系统存储优先于旧 env；显式空环境也不偷偷退回存储 key。
- `provider-settings.mjs` 集中四个现有 provider 的 catalog / 能力和模型选择；GUI 不引入 Pi。显式测试使用同一选择逻辑，单个短请求、128 token 输出上限、15 秒超时、禁用 SDK 重试；只有有效文本响应才成功。401/403、404、超时、缺 key 与无效响应都有安全失败状态，不向用户回显服务端原始错误或 key。
