## 1. 产品定位

> Aside 是围绕用户当前工作获取上下文、组织本地资料与记忆，并通过统一交互调用不同 agent 的 ambient 工作入口。

用户在 Aside 发起和继续工作，底层可以由 Codex、Claude 系 agent 或现有 Pi 实现执行。Aside 持续积累的是用户的工作上下文、资料关联、记忆和任务交互体验；这些积累应能在更换执行引擎后继续使用。

2026-10-17 的讨论把长期投入重心放在 context capture、文件与记忆，以及可替换 agent 的能力上。2026-10-31 进一步明确执行先后：先修正前端路线、清理旧债并补齐当前 runtime，暂不为长期可替换性启动外部接入或 runtime 重写。

## 2. 用户明确的方向

- 核心是 context capture、接近零配置的易用性与 ambient agent 体验，不绑定自研 runtime 或 Pi core。
- 优先考虑复用厂商原生 agent 的能力与模型适配，不要求用户为了 Aside 的交互体验改用 Aside 自己的 agent 实现。
- 后续研究围绕更完善的上下文获取、本地文件管理、memory、自整理，以及更深地参与用户的当前工作展开。
- 尝试兼容接入 Codex、Claude Code 等，让它们通过 Aside 的界面和交互工作。
- Aside 保持用户的一线入口；context capture MCP 可以成为实现或开放方式，但不会因此成为只向其他客户端提供数据的后台服务。
- Mac 是需要保留的演进方向，因此平台专属外壳的投入需要重新权衡。具体迁移时点尚未确定。

同日后续讨论进一步提出：接入外部 agent 时，尽量让用户自行负责安装、登录、模型配置与连通性，Aside 负责界面、消息收发和上下文交接；memory 与文件管理规范优先通过 skill 和普通文件提供。即使继续开发自研 agent，也应避免让产品依赖只有自己的 runtime 才能提供的深度控制或私有 tool。这是需要继续考量和验证的收敛方向，尚未选定具体接入协议。

后续用户已明确采用“全局快捷键呼出／隐藏”，同时保留快捷键自动采集原窗口 context、80/20 全高并排、再次按键恢复原窗口的核心交互。此前误删的自动排列／恢复已在 R1 按 FE-07 恢复，连续底板与白色实体组件也已落实；R3 补动态外部焦点 Capture。当前设计见 [设计决定](./design/SUMMONED-SIDEBAR.md)，源码与未完成的真实桌面验证边界见 [FRONTEND-REVIEW.md](./FRONTEND-REVIEW.md)。Ambient 的价值应通过少解释、少配置、能接续工作体现，桌面常驻不是前提。

## 3. 建议的职责分工

以下是基于方向的架构建议，尚未落为接口规范。

| 部分 | Aside 应积累的能力 | 与执行引擎的关系 |
| --- | --- | --- |
| 上下文获取 | 当前应用、文件、选区、页面与任务关联；来源、时间、版本和可用性。 | 以可解释的数据和引用交接给不同 agent。 |
| 本地资料管理 | 资料身份、索引、原始位置、快照、派生文件、产物去向及关联。 | 为执行任务提供合适路径和资料，接回产物与结果。 |
| 记忆 | 工作续接、已确认事实、偏好、决定及其来源。 | 按任务选择和供给，不依赖单一厂商的会话存储。 |
| 用户交互 | 唤起、输入、上下文预览、任务进度、审批、取消、结果回看。 | 将各引擎事件呈现在 Aside 中，保留有意义的原生差异。 |
| 执行连接 | 启动或连接 agent、设置工作目录、传入上下文、映射会话和收取事件。 | 保留必要的连接与协调代码，避免重新建设 agent loop。 |
| Agent 本体 | 优先复用厂商维护的推理循环、模型适配、原生工具和会话机制。 | 现有 Pi runtime 可以暂作过渡实现，去留由后续验证决定。 |

因此，“不以 runtime 为核心”仍需要一层薄的执行连接。只传环境、路径、规则可以证明上下文交接；要让用户始终在 Aside 中工作，还需要接通输出、审批、取消、恢复和错误。

用户资料与可复用记忆归 Aside 管理；厂商原生会话保留自己的身份与状态，通过映射连接。跨引擎接续优先验证“用资料和摘要继续工作”，原生会话无损迁移仍是独立问题。

## 4. Context、文件、记忆形成一条链

建议按下面的关系设计，而不是把 capture、文件索引、memory 做成互不相干的功能：

```text
当前工作 → 获取与辨认上下文 → 关联资料和任务 → 选择相关记忆
         → 交给选定 agent 执行 → 接回产物、决定与进度 → 更新工作资料
```

### Context capture

目标从“抓到屏幕上的文字”推进到“知道用户此刻在处理哪份资料、哪个任务，以及应交给 agent 哪些内容”。优先研究现有宿主策略的覆盖与准确性、文件身份、来源关联、切换任务时的区分和失效判断。

当前一次性采集协议已经包含来源、时间、过期和路径描述等信息，可以作为起点。持续感知、后台触发和长期保留会扩展现有边界，仍需明确触发条件、工作范围、更新方式和用户控制，不能把它们视为已经实现。

### 文件本地管理

建议先区分用户原文件、Aside 管理的引用或快照、agent 生成的产物，以及可重建的索引。优先减少找路径、说明位置、寻找产物的负担，并处理改名、移动、版本变化和失效引用。

自整理可先从标签、关联、任务归档、去重提示和产物归属入手。是否移动或重命名用户原文件、是否复制到 Aside 管理的资料区，以及如何撤销，仍待决定。

### Memory 与自整理

建议区分当前任务的工作状态、历史任务的摘要与决定，以及长期稳定的偏好和事实。保留来源与时间，让记忆可以被查看、纠正、失效和删除；资料索引与可用记忆也应能独立于 agent 会话存在。

记忆的形成、检索和更新需要围绕“下次能否少解释、准确接续”验证。全量保存聊天、引入向量库或扩大采集量，本身不能证明这个目标。自动保留的默认范围、推断内容的地位、冲突处理，以及各引擎原生 memory 如何并存，均待研究。

### 工作索引：用户 2026-11-05 明确的 vision

这一节修正上面“三层记忆”的取舍：**本产品的 memory 是第二层（工作索引），不是第三层（内容式个人数据）。**
用户明确不要“记住用户喜欢用什么软件”那类个性化记忆。

**要解决的问题。** 用户同时在推进几件事（例如开发一个软件、写自己的简历）。传统做法是为每件事
建一个工作区，每次继续做都要自己找上次的会话、判断是新建还是接着做。Aside 的目标是让用户
**不再维护工作区**：只需要说要做的事，由系统判断它属于哪个已有工作。

**理想流程。**

```text
第一天：开发软件      → 新建工作记录 A
第二天：写简历        → 与记录均不相近，新建工作记录 B
第三天：继续开发软件  → 与 B 不相近、与 A 相近，归并进 A
```

**边界（用户已确认）。**

- **capture 始终手动**，只有快捷键一个入口。自动判断“用户此刻在做什么”是越界，不是优先级问题。
  这一点在可预见的未来不变。
- 记录是**索引式**的：任务、涉及的文件、产物、时间、一句话结果，以及任务之间的关系。
  不是偏好库、不是对话摘要、不是向量检索。
- **判断归属交给模型**，读索引后决定；用户不满意时可以要求分离或归并。分离与归并都是改普通文件，
  与改一份文档没有区别。
- 索引必须是**可读、可改、可删的普通文件**，关闭 Aside 后也能直接查看和带走。

**尚未确定的部分。** 索引的字段与文件布局；与现有 `continuation`（目前只在单个会话内有效的
workspace 延续）如何衔接——跨会话是这套设计成立的前提，也是实现时第一个要解决的问题；
归并判错的容忍度与纠正成本；同一文件被两条记录引用时产物如何归属。

**与 v1 的关系（沿革）。** 2026-11-05 草案将完整链路列为 V1.6 承诺与旧 F 组验收。2026-11-08 曾建议 R1 只做显式续接、智能归属推到 R2，但这不是用户确认的范围。本次澄清后，[范围定义](./V1-SCOPE.md#3-工作记录与续接的有限定义)分成基础会话 / 产物交付，以及可选项目归纳 / 检索；后者发布阶段待确认，不能用前者冒充 memory。

### 2026-11-08 补充：归纳文件夹与项目记忆

状态：**产品讨论共识与最小方案草案，用户同意记录并提交；不是实现 plan，也不代表 R1 / R2 排期已经冻结。** 下文区分体验目标、当前事实、技术建议与待决定项，后续讨论先对齐再落成要求，不能把助手的建议直接升级成用户命令。

**最终目的：免于配置和选择。** 用户打开 agent，说起前几天做的事，不用先选工作区或旧会话，就能找到相关历史和文件目录。能直接延续旧会话时自然延续；新会话也能接着做，不强制跳回旧聊天。连续的是工作，不一定是会话窗口。这里将项目历史本身视为 context，是 context capture 理念的延伸，不是另建全局个人档案。

**概念模型。** 会话是工作经历的记录本体；项目是相关会话的轻量归纳；工作区是工作涉及的目录引用 / 执行环境参数。会话并非全部数据：原始资料与产物仍是独立文件，会话记录不能替代它们。项目不等于目录，不要求建立严格的一一对应：一个项目可引用多个目录；桌面等同一目录也可被多个项目引用。先满足关联，不预建复杂任务本体、关系图或细粒度多主题模型。

**当前实现，而非未来承诺。** 会话默认保存为 `%LOCALAPPDATA%/Aside/sessions` 下的 JSONL（可通过 `ASIDE_SESSION_ROOT` 覆盖），使用独立的 `aside-session` 存储分组；文件来源 / 输出目录由 capture、显式路径或默认输出目录决定，私有会话库属于受保护路径。`continuation` 是会话内的工作状态，不是跨会话项目索引。来源：`agent-runtime/src/session.mjs`、`task-workspace.mjs`、`output-workspace.mjs`。

**最小组织形态。** 在已有本地会话外包一层逻辑项目文件夹，只需简单 README、相关会话引用、若干资料 / 工作区 / 产物引用。README 说明这是什么工作、当前进展与重要资料位置，不复制完整聊天，不抽取个人偏好。优先组织已有东西，不移动原始会话或用户文件；具体物理布局和字段尚未决定。

```text
项目 A（逻辑归纳）
  README：工作说明、进展、关键位置
  会话引用：会话 1、会话 3
  目录引用：桌面、代码目录、资料目录
  产物引用：实际生成的文件
```

**最小运行路径建议。** 新请求 → 查看简短项目目录 / README，判断归属 → 在匹配项目内按需读取相关会话和文件引用 → 检查路径与现有访问规则，自动选用相关工作目录 → 执行并保存会话、实际产物关联，必要时小幅更新 README。找不到明确关联时不强行借用无关历史；必要歧义才询问，不把选择项目做成固定前置步骤。开关开启是前提，具体归属 / 新建规则待 plan 验证。

例如“把前几天的报价表新增一档企业版”，系统应找到对应项目、旧会话中的约定及报价文件位置，在新会话继续，而不是要求用户先找到目录。项目索引不等于执行 cwd，但可以用来自动路由目录；此前“不自动切换工作区”的说法过严。自动选择不等于恢复旧授权，路径失效或越过权限边界仍需正常处理。

**复杂度与 token 约束。** 依赖当前 agent 的判断和普通资料读取，先不引入独立分类 agent、向量数据库、多级记忆、全历史摘要或后台周期性整理。先读小目录，再读命中项目的 README，必要时才读相关历史；复用当前会话已明确的项目关联，不每轮全局重判。README 只在有实质进展时小幅更新，不每条消息重写，也不为记忆额外增加固定多轮模型调用。这些是设计取向，尚无耗时 / token 实测，不承诺零成本。

**克制边界。** 普通会话保存、运行留痕和产物打开入口是基础功能，不叫 memory；项目记忆才是跨会话利用相关工作的能力。关闭记忆不应破坏基础功能，也不跨会话读取历史。关闭时是否仍归纳，当前建议是不默认继续分析，尚待明确。归纳 / 检索是否共用开关、最小匹配数据是否出站也待定。

引用桌面不表示桌面上的所有文件都属于该项目；匹配项目也不表示其全部内容都与本次任务相关。不通读全部聊天来分类、不默认整包注入历史、不扫描任务外环境，不提取全局个人画像。保留历史来源、必要的排除 / 纠错能力；同一项目仍可能包含私人话题，不能宣称仅凭归属就保证隐私。历史是资料而非新授权或高优先级指令，目录访问边界不能只靠 prompt。

**留给后续的具体问题。** README / 引用存储布局、归属判断与不确定时的退路、记忆开关语义、更新时机、敏感会话排除与纠正、删除 / 失效引用处理、如何在当前受保护会话库边界内提供按需历史。先以最小用例验证可靠性与成本，再决定是否需要额外机制；不因列出问题就增加独立子系统。R1 / R2 归属仍待确认，不开始实现。

2026-11-08 当前捕获口径：保留既有快捷键和界面显式 Capture，禁止后台持续采集正文；焦点元数据监听不是自动 capture。前述“只有快捷键”的历史描述不能用来删掉已经存在的显式 Capture 功能。

## 5. 零配置与 Ambient 的体验目标

同日后续讨论将一个更薄的接入方式列为优先考量：用户先让原生 CLI 安装、登录并可独立工作，Aside 在此基础上尽量做到零额外配置。对应的初期用户会更偏向已有 CLI 使用者；面向完全没有配置 agent 的用户，开箱即用程度会降低，这是需要明确接受的产品取舍。

Aside 可以发现可用引擎、准备工作范围、资料和产物位置，并展示就绪或失败状态。首次登录、provider、代理与模型连通性由用户在原生工具中处理；认证流程和凭据管理不作为 Aside 接入的必备职责。原先全链路零配置的设想保留为更长期的体验候选，不作为这条薄接入路径的前置要求。

Ambient 应体现为用户不必反复交代“我在哪里、我在做什么、上次做到哪一步”，任务在隐藏界面后仍可接续，需要决策或查看结果时能回来。捕获范围和长期记忆的控制应以用户能理解的工作对象呈现。

## 6. 外部 Agent 接入：未来 feature 的研究存档

**2026-10-31 处置：整体延后。** 本节保留前次查阅和讨论，不安排当前验证，不承诺已兼容，也不重新断言资料在未来接入时仍适用。

截至 2026-10-17，以下仅来自官方文档，尚未在 Aside 中运行验证。

| 候选 | 官方文档显示的程序化入口 | Aside 仍需验证 |
| --- | --- | --- |
| Codex | App Server 面向自定义客户端，涵盖认证、会话历史、审批与流式 agent 事件；文档提供本地 stdio 通信方式。 | 上下文供给、已有登录、会话续接、原生能力保留、审批映射、取消，以及实际版本兼容性。 |
| Claude 系 agent | Agent SDK 可程序化使用 Claude Code 的 agent；CLI 也提供 `-p` 与结构化输出，SDK 有审批回调和会话机制。 | 适合本地桌面产品的接入方式、能力与配置加载差异、会话与审批交互，以及认证与使用方式。 |
| Context MCP | 可以作为对 agent 暴露上下文、资料检索和记忆的候选接口。 | 它只解决部分上下文供给；完整入口还需要独立的执行与交互连接。具体协议未选定。 |

Claude Agent SDK 官方说明：未经事先批准，第三方产品不能提供 claude.ai 登录或复用其额度，应使用其说明的 API key 认证方式。因此，不能把“用户已有 Claude 订阅便可直接用于 Aside”写成承诺。具体产品接入路径仍需进一步核实。

各 agent 的原生工具未必经过现有 Aside PermissionBroker。接入时需核对各自实际提供的审批、沙箱与事件控制；旧 Pi 路径上的逐次授权保证不能直接套用到外部 agent。

建议按能力声明兼容程度，保留原生事件以支持必要的专属交互，不先压成所有引擎都只能满足的最小功能集。优先探索正式的程序化接口，避免把解析终端画面作为主要连接方式。

### 后续讨论：消息接入、文件交接与 Skill 优先

用户希望考量的目标是“对 agent 零耦合”。建议将工程含义定义为：**不依赖 agent 内部实现、专属 loop hook 或 Aside 私有工具；公开的消息协议、skill 加载方式和文件格式保留最小适配。** 所有通信仍需要约定输入、输出和版本，因此不承诺字面上的零适配。

| 参与者 | 候选职责 |
| --- | --- |
| 用户与原生 CLI | 安装、登录、provider 和模型配置、网络连通性，以及原生执行权限。 |
| Aside | 获取上下文、准备可读资料、管理自己的本地数据、提供交互、提交请求、接收和展示结果。 |
| Skill 与普通文件 | 描述资料入口、记忆检索与更新步骤、文件命名和产物约定；使用 agent 已有的读写能力。 |
| 很薄的引擎适配 | 调用公开程序化入口、设置当前任务路径、映射会话和终止状态；按接口能力转达审批、取消和失败。 |

对 Codex，官方文档提供了一个可验证的起点：`codex exec --json` 输出 JSONL 事件，默认复用 CLI 已保存的认证，也支持按会话 ID 续接。App Server 则提供双向请求与事件，支持审批交互，并可显式提交 skill 输入。可以先验证单次任务的收发和文件交接，再判断是否需要 App Server；两者在交互能力上不能视为等价。

用户负责 CLI 就绪能够缩小 Aside 的职责，但不自动改变各厂商对程序化调用和第三方产品使用的条件。前面的 Claude SDK 认证说明仍按其适用接口保留，接入方式需要逐项核实。

Skill 适合承载可迁移的行为约定。例如，任务开始时读取哪些相关记忆、把新决定写到哪里、怎样标记来源，以及新产物如何命名和归档。优先显式加载或调用，而不是依赖 agent 自行猜测是否要使用。每次具体任务的上下文和路径应另外交接，避免把一个长期 skill 改写成混杂所有任务的动态状态文件。

Skill 是对模型的说明，无法单独保证每次执行、写入成功、并发一致性或文件约束。建议让 agent 用普通文件记录可检查的摘要或候选更新；Aside 负责自己数据的保存、校验、索引和必要合并。哪些整理交给模型、哪些由确定性代码处理，仍待验证，不默认把整套 memory 可靠性寄托于提示词。

自研 runtime 也应遵守同样的接入约束：核心工作先验证能否通过现成读写能力、普通文件和 skill 完成，再考虑增加内部能力。专属 tool、hook 或内部状态操作只作为可选增强，不成为基础体验的唯一实现路径。

独立脚本、普通本地 CLI 或标准 MCP 可在确有需要时补充确定性行为；是否引入取决于实际缺口。增加工具时也应保留清楚的输入输出与独立使用方式，避免重新形成对某个 runtime 私有注册机制的依赖。

建议的检查标准：关闭 Aside 后，用户仍能用原生 CLI 读取同一批资料和规范继续任务；更换引擎时，主要替换消息及 skill 适配；移除 Aside 专属 tool 后，基础上下文、资料与记忆工作流仍成立。连续性以资料和摘要为基础，不据此承诺原生会话状态完全一致。

薄接入仍需处理所选接口会发出的必要交互。若有审批或输入请求，界面须能转达或明确停止；不为简化接入而自动批准、绕过原生策略或把等待状态当作完成。完整厂商功能覆盖不作为第一轮收发验证的前置条件。

## 7. 当前顺序：前端收束、遗留清理、现有 runtime 补齐

2026-10-31 用户决定已取代此前“先接一个 CLI、再接第二个”的建议。以 [RECOVERY-PLAN.md](./RECOVERY-PLAN.md) 为唯一当前跟踪入口：

2. 复核历史审计修复，解决仍成立的缺陷，补当前界面与 runtime 集成证据。
3. 明确自研 runtime 的有限必需功能清单，补齐保留范围；功能 backlog、已接受限制和延期验收分别记录。
4. 至少在 runtime 功能齐备后，再为 Codex/Claude Code 薄接入提出独立 feature 需求与验证计划。

当前先验证既有执行路径是否可靠地完成真实任务。更换 agent 后保留资料、记忆与交互的目标继续有效，留到外部接入 feature 验证。

Windows 与 Mac 的采集适配、文件和数据模型、agent 连接应分别设计边界。保留现有跨平台外壳不等于已完成 Mac 上下文适配；平台投入顺序仍待决定。

## 8. 后续 feature 仍需收敛的问题

以下不构成当前待办；当前问题先查收束计划。现有 runtime 的实现不需要为解决这些未来问题而提前重构。

## 9. 2026-11-03 用户提出的界面方向

记录于此供后续讨论，不是当前待办，也不要据此提前重构现有面板。

**1. 侧栏比例可调宽（用户确认可做）。** 当前分屏固定为 20%，由
`src-tauri/src/workspace.rs` 的 `side_layout` 用整数除法 `(width + 2) / 5` 写死，
只保证互补取整，没有配置入口。

用户明确的形态：**右侧始终吸附屏幕边缘，宽度向左增长**。这比“两边都动”简单得多，
也不会出现面板离边缘留缝的情况。按此实现时：

- `side_layout` 接受宽度或比例参数，仍然只计算右侧段；`agent.x = work_area.x +
  target_width` 的既有写法天然保持右吸附，不需要额外锚定逻辑。
- 扩大宽度时向左吃掉目标窗口的空间，`target_width = width - agent_width` 保持互补，
  目标窗口继续贴在左侧；这一点与现有 `layout_uses_complementary_full_height_segments`
  的语义一致，只需把常量 0.2 换成参数。
- `commands.rs` 的 `MIN_PANEL_WIDTH` / `MAX_PANEL_WIDTH`（340–520）只在 `resize_agent`
  里生效，不约束自动分屏，但会阻止手动拉宽；可调比例落地时必须一起放开，否则两种
  宽度来源会互相打架。
- 需要定：比例存在设置里（则跟随 P0 的 schema 与空闲应用语义），还是每次呼出时临时
  生效；以及上限如何与目标窗口的最小可用宽度协调（窄屏上把目标挤到不可用不是有效
  配置）。
- `SUMMONED-SIDEBAR.md` 的“严格互补 80/20”表述要相应改成“互补可变比例”。

**2. 设置与会话界面改为独立临时窗口。** 用户希望 settings 不要挤在 20% 侧栏里，
而是单独开一个正常尺寸的窗口，用完关闭。

现有实现**没有硬性限制**，但也不是为多窗口设计的：

- `tauri.conf.json` 只声明了一个窗口（`decorations: false`、`transparent: true`、
  `resizable: false`、`skipTaskbar: true`），这是侧栏常驻窗口本身。
- `SettingsPanel` / `SessionPanel` 只是 `App.tsx` 里的条件渲染，共用同一 React root
  与同一 `onRuntimeEvent` 订阅。没有独立窗口、路由或第二入口。
- 会话与设置状态由原生 `SettingsManager` / 运行时进程持有，IPC 是
  `invoke` 命令 + 事件广播，本身不绑定某个窗口；新增一个窗口在数据层是可行的。
- 需要处理的是：新窗口的创建 / 关闭生命周期、关闭时侧栏状态是否需要刷新、
  键盘焦点与置顶行为、以及事件是否要按窗口路由。这些都要单独设计，不能只加一个
  `WebviewWindow` 就算完成。

**3. MCP 配置放进 Settings（2026-11-03 用户决定）。** MCP 配置不做独立入口，
其余设置项一样放在 Settings 内。这与 Cycle 8 最初的分页设想一致
（“模型与 API / 文件与存储 / MCP / 诊断”），因此 P5 直接实现为 Settings 中的
一个分区，不新增侧栏按钮或第三个面板。

这个决定同时解掉了第 2 点里悬着的问题：既然 MCP 跟随 Settings，**窗口方案只需要
定一次**，P5 不会产生一份之后要搬迁的界面代码。设置的独立窗口若实施，MCP 分区随之
一起进去；若不实施，MCP 也只是 Settings 面板里的另一张卡片。

**4. 与当前批次的关系。** P5 可以在现有 Settings 面板中落地，不被窗口方案阻塞；
两者解耦后，窗口优先级由用户按需要排，不需要为 P5 让路。
